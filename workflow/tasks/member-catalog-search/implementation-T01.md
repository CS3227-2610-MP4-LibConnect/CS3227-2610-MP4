## Candidate contract for the data-model decision

The choices below are concrete proposed implementation details within the approved R2–R6 behavior. They remain provisional until the storage/query decision is approved and reviewed.

- `GET /api/member/catalog`, same-origin, cookie authenticated, read-only. Reuse trusted session validation and recheck current active `MEMBER` account on every request. Return 401 for missing, expired, or invalid session; 403 for a verified non-member; 400 for unsupported or malformed query parameters; 503 with a generic body for storage failure. Return no Book fields in any error.
- Only query keys: `q`, `title`, `author`, `publisher`, `category`, `isbn`, `synopsis`, `minYear`, `maxYear`, `pageSize`, `cursor`; duplicates and any other key return 400. Text fields are strings trimmed at both ends, at most 100 Unicode code points after trimming; an empty value has no effect. `synopsis` query is also capped at 100. Year strings must contain exactly four ASCII digits, with inclusive supported range 1450–2100; `minYear > maxYear` returns 400. `pageSize` is an ASCII decimal integer from 1 to 100, default 100; the UI uses 100. `cursor` is at most 4096 ASCII characters and must decode to a versioned, strictly validated object. Validation happens before Book access.
- Normalize text by trimming query edges and applying one documented Unicode case mapping to both query and Book field; compare contiguous substrings. Basic `q` matches title OR author. Each populated advanced criterion and the basic clause combine with AND. Missing optional Book fields are treated as empty strings; a filter on one cannot match an absent value. A missing/invalid ISBN, title, author, or publication year makes the document invalid and it is skipped, counted in safe aggregate diagnostics only. The precise types, validation limits, and uniqueness of these Book fields depend on the approved storage contract. A missing optional synopsis becomes an empty string and the card displays a neutral “No synopsis provided” message.
- Success shape: `{ books: [{ isbn, title, author, synopsis }], nextCursor: string | null, scannedValidBooks: boolean, scanComplete: boolean }`. No user or session data. The client accumulates `scannedValidBooks` across continuation responses for one query. When `scanComplete` is true, zero results plus no valid Books scanned means catalog empty; zero results plus any valid Book scanned means no match. Until then, it must show a continuing-search state, not either conclusion. A success response's exact field types and absence of extra fields are validated by the client before display.
- Cursor proposal: base64url encoding of a strict versioned JSON object containing the last scanned document ID, normalized-filter SHA-256 digest, and page size. It is opaque to the UI, bound to the current criteria, and rejected on malformed encoding, unknown fields, impossible ID, or digest/page-size mismatch. It is **not an authorization credential**; the server authenticates each request. A forged but syntactically valid position could skip items only in that caller's results; if tamper resistance is required, use an approved signing-key configuration or server-held state. That additional configuration has not been approved.
- Proposed continuation: a clearly labelled “Load more books” button when `nextCursor` exists, including when a scan chunk produced zero matches. It appends cards for the same submitted query and shows a page-loading state. Search, Clear, collapse, navigation, and logout discard the old cursor/results and invalidate older responses. A 401 follows the protected-route signed-out behavior and hides cards; 403 or malformed 200 fails closed with cards hidden and a non-sensitive access/retry state; 503/network failure shows a retry action for that page without claiming empty/no match.
- Cards show title, author, and synopsis as text. A line-clamped synopsis includes an explicit keyboard-operable “Read full synopsis” expansion so sighted and assistive-technology users can read all text. It does not interpret markup. This is a proposed card interaction consistent with R4.

## Scan invariant and unresolved cost

**Candidate Firestore strategy, contingent on approved Book collection/schema:** order all documents by immutable document ID; request `limit(pageSize)` starting after the prior scanned ID; validate every returned Book; apply all criteria in trusted server code; emit the matching valid Books from this raw chunk; set `nextCursor` to the last scanned ID whenever a full chunk was read. A full final chunk may require one extra empty request. Every response reads at most 100 Book documents plus the account/session reads. With a static collection and a correct cursor, each document lies in exactly one non-overlapping ID interval, so every valid matching title appears exactly once after following all continuations. An insertion before the cursor or mutation during browsing is outside the snapshot guarantee; refreshing starts a new traversal. This satisfies normal-browsing ordering, not real-time synchronization.

This **does not** establish a bounded complete search cost. For `N` Book documents it may read `N` documents across `ceil(N/100)` or more requests, and `N` is unknown and unbounded by current local evidence. A fixed total scan cap would leave matches unreachable and violate R2/R5. A search index or precomputed n-gram structure might improve cost, but would add schema/index/write maintenance and possibly a dependency or configuration; none is approved. The design cannot be finalized by assuming a small catalog.
