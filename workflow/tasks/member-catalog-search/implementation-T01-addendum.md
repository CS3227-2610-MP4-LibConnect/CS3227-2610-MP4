## Revised read and response contract

Read `db.collection('books')` in ascending Firestore document-ID order, in raw chunks of 100 with `startAfter(lastScannedDocumentId)`. Read only the seven `Overview.md` Book fields from each document's data: `isbn`, `title`, `author`, `publicationYear`, `publisher`, `category`, `synopsis`. Do not read `BookCopy` or member data through this adapter. The human confirmed that each `books` document ID is its ISBN and that `isbn`, `title`, and `author` are required nonempty strings while `publicationYear` is an integer. Validate these on read: `isbn` is a string with nonzero length, no surrounding whitespace (`isbn === isbn.trim()`), and exact equality to the document ID (`doc.id === isbn`); `title` and `author` are strings with nonempty trimmed content; `publicationYear` is a JavaScript safe integer. The ID comparison is exact string equality, with no ISBN case folding, punctuation stripping, migration, or write-back. As a remaining read-parser proposal, `publisher`, `category`, and `synopsis` are strings or absent, with absence represented as empty text. A required field missing or wrong-typed, an ID/ISBN mismatch, or an optional field present with a wrong type makes that document invalid and it is skipped without a write or raw-value log. Since Firestore document IDs are unique and must equal each valid Book's ISBN, each valid ISBN appears in one ordered scan position and yields at most one card; the same immutable ID cursor avoids duplicates or skips in a static collection. The parser does not change stored documents or assert that current data was inspected.

The proposed success shape gains `scannedAnyDocument: boolean` for the **current raw chunk**. Keep `scannedValidBooks: boolean` for that chunk, `books`, `nextCursor`, and `scanComplete`. The client accumulates both flags across one complete query traversal. At completion with no matches: no raw documents across chunks means the specified “No books found” message; raw documents but zero valid Books means a distinct generic catalog-data error, never an empty-catalog or no-match assertion; at least one valid Book means “No matching books” for active filters. A collection with seven malformed documents cannot be described as empty. The all-invalid error's wording is a UI detail for review and exposes no Book data. This addresses independent-review finding 2.

Text normalization is JavaScript `String.prototype.trim()` then `String.prototype.toLowerCase()` on both query and stored strings, followed by `includes()`. This uses the deployed Node runtime's Unicode default lowercase behavior, not locale-specific collation or full Unicode case folding. The same rule must be used in synthetic tests. Cursor `lastScannedDocumentId` must be a nonempty string of at most 1,500 UTF-8 bytes, contain no `/` or NUL, and not equal `.` or `..`; malformed structure is 400 before Book access. Cursor metadata remains bound to normalized criteria and page size, and is not authority. These details respond to independent-review finding 3, subject to implementation confirmation against Firestore document-ID constraints.

## Conditional bound and continuation beyond expectation

The dependency-free `scan-demo.mjs` exercised 0, 1, 100, 101, and 1,000 raw documents, with the sole `tom` match in the last document of every nonempty case, plus seven all-invalid documents. It asserts exact reads and requests; command and output are in `implementation-T01-log-addendum.md`. With at most 1,000 raw `books` documents and 100 raw documents per request, complete traversal reads at most **1,000 Book documents** and needs at most **11 catalog requests** (an extra empty request terminates an exact multiple of 100). This excludes separate session/account reads and Firestore billing overhead. The premise is the human's expected maximum, not an enforced storage limit or observed count.

If `books` exceeds 1,000 documents, the server **continues** cursor traversal in 100-document chunks. It does not truncate matches. Total reads and requests then exceed the expected budget. There is no hard cap that would violate R2/R5 reachability. The expected threshold warrants monitoring or architecture review before it is treated as a service guarantee. No external Firestore access was made. This addresses the expected-volume portion of independent-review finding 1 conditionally, but does not prove actual production volume.
