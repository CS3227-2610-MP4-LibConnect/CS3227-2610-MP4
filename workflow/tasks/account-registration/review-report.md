## Findings and follow-up

1. **Low — email syntax policy ambiguity.** `server/auth/register.js:14–31` accepts any nonblank bounded string as `email`; a local probe found `not-an-email` and `a b@example.test` both accepted. `RegistrationPage.tsx` uses `noValidate` and likewise has no syntax check. The approved specification R4 says to reject malformed values but explicitly defines only blank/byte limits and canonicalization for email. Before adding a new syntax rule, the analyst should clarify the intended email format in the specification, then add matching server/client tests and validation if required. This is a policy follow-up, not evidence that the approved explicit bounds were missed.
2. **Low — retained notice can outlive the registration page.** `RegistrationPage.tsx:36` stores a success marker as soon as a valid 201 is received; `LoginPage.tsx:7–23` consumes it only when login renders. If a visitor completes a registration, reloads `/register`, then makes a failed later attempt before visiting login, the older notice can appear at login. Consider clearing any older marker on a fresh registration attempt if notices must describe only the latest attempt. No authorization decision relies on the marker.
3. **Verification limit — real Firebase and deployment.** The fake transaction serializes writes; it does not prove Admin SDK behavior during real transaction contention, Firestore rules/IAM, proxy source identification, or deployed SPA routing. Validate these in an authorized emulator/deployment stage before release. The server timestamp is a server `Date` created before commit, not a Firestore server timestamp; it meets the current server-generated timestamp wording but may precede a delayed commit.

Security review is in `security-review.md`. No review-only test file was added. The direct `node -e` probe used synthetic strings only.

### T06 findings

1. **High, blocking — production can use developer ADC despite R8.** `src/libconnect-mp4/server/firestore-target.js:18–26,76–80` treats a nonempty `K_SERVICE` environment variable as deployment evidence and calls Firebase Admin `applicationDefault()`. The installed `google-auth-library/build/src/auth/googleauth.js:264–289` checks `GOOGLE_APPLICATION_CREDENTIALS`, then a well-known gcloud ADC file, *before* checking GCE/Cloud Run metadata. Rejecting `GOOGLE_APPLICATION_CREDENTIALS` therefore does not prevent use of developer ADC from that file, and a matching project environment variable does not authenticate the credential's origin. A production-mode process can start with the wrong credential source and discover validity only on a later request. This violates R8's runtime-credential-only, no developer ADC, and fail-closed requirements. **Required T06 correction:** select and validate the deployment runtime metadata identity explicitly for production, verify its project against the configured production project before listening, and add isolated tests for the well-known ADC precedence case without reading real credential files or contacting cloud services. Return the corrected T06 implementation for independent review. No live production probe was performed.
2. **Low, follow-up — emulator test data/rate counters persist.** The opt-in integration creates synthetic records in the running local emulator and does not delete them; repeated tests may reach the approved five-attempt source limit. The test passed on this review run. Use a fresh isolated emulator or wait for the counter window for repeatability; do not clear shared emulator data without authorization.

Earlier low-severity email-syntax and notice-lifetime observations remain follow-ups, not T06 blockers. The revised spec's scenarios 13–17 are verified locally except the production runtime identity and credential-origin criteria. Real production IAM, Firestore rules, and deployment remain separately gated and unverified.
